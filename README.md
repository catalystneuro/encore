# Encore Science: the registry

Encore Science checks datasets against the papers they came from. This repository holds its public record, the Encore registry, served at <https://encorescience.org>, and the `encore` command that runs the same check on your own data ([docs/encore.md](docs/encore.md)). It is developed by [CatalystNeuro](https://www.catalystneuro.com).

Agents, and people, try to reproduce the key findings of papers from the open
data in public archives, starting with the [DANDI Archive](https://dandiarchive.org), and register the result
here: the notebooks when it works, and the reason when it does not.

- **For the archive:** evidence of whether each dandiset is complete and
  accurate enough to support the findings of its paper.
- **For analysts:** working notebooks to build new analyses on.

Status: pilot. All eight pilot targets have been attempted and checked by an
independent agent.

**Dashboard:** <https://encorescience.org/>

## Reading the outcomes

An outcome says what one attempt could recover from the data in a dandiset,
with the methods available to it. **A "not reproduced" or "partially
reproduced" outcome is not a finding that the paper is wrong.** It can come
from a mistake or a limitation in the agent's analysis, from methods the paper
does not describe fully, from data that is not in the dandiset, or from a
dandiset that differs from what the paper analysed. Most attempts here are
made by AI agents. An attempt marked as verified has been checked by a second,
independent agent, but neither is infallible. Each attempt records its reasoning, how its
analysis differs from the paper's, and its code, so that anyone can check it.

If you are an author of a paper listed here and think an attempt is wrong,
please [open an issue](https://github.com/catalystneuro/reproduction-registry/issues).

## What is here

- [`docs/design.md`](docs/design.md): the design, phasing and open decisions.
- [`docs/protocol.md`](docs/protocol.md): what an author and a verifier do in an attempt.
- [`docs/pilot-notes.md`](docs/pilot-notes.md): what each pilot attempt taught.
- [`targets/dandisets.json`](targets/dandisets.json): the queue of targets,
  dandisets that name a paper, generated by
  [`tools/build_targets.py`](tools/build_targets.py) from the public DANDI API.
  [`targets/description_papers.yaml`](targets/description_papers.yaml) adds the
  papers that a dandiset's description, but not its metadata, names as the
  source of its data.
- [`targets/pilot.yaml`](targets/pilot.yaml): the eight targets for the pilot.
- [`claims/`](claims): for each target attempted, the findings of the paper
  that were tested.
- [`attempts/`](attempts): one record per attempt, with an outcome for each
  claim, whether or not it worked.
- [`entries/`](entries): the notebooks.
- [`schemas/`](schemas): draft schemas for the files above.

## Agent runs

Attempts by agents are made in GitHub Actions, one role at a time, on the
subscription token in the `CLAUDE_CODE_OAUTH_TOKEN` secret. With
`-f account=unverified` they use `CLAUDE_CODE_OAUTH_TOKEN_UNVERIFIED`
instead; the runner tries that account first and moves a run it flags to the
verified one ([docs/pipeline.md](docs/pipeline.md#accounts)):

```bash
gh workflow run attempt.yml -f dataset=000147 -f role=author
```

An attempt starts with the reader's runs, which write the claims file from the paper,
in the [Paper run](.github/workflows/papers.yml) workflow:

```bash
gh workflow run papers.yml -f dataset=000147 -f role=claims
```

The roles, in order, are `claims` and `claims-check` (Paper run), then
`author`, `answer` (Paper run) and `author-answers` when the author asked
questions, `verifier-1`, `author-revise-1`, `verifier-2` and
`author-revise-2`, then `verifier-3` and `author-revise-3` when the final
revision proposed a change of outcome. The papers are kept in a private
repository that only these workflows can read, from `main` ([docs/pipeline.md](docs/pipeline.md)).
To run whole attempts on several datasets at once, each going through the
roles in order:

```bash
gh workflow run pipeline.yml -f datasets="000628 000939 DANDI:001075" -f max_parallel=3
```

All runs share the subscription's usage limits, so more in parallel reaches
them sooner. Each run commits its changes and its
cleaned transcript and report to the branch `attempt/<dandiset>`; a person
reads the transcript and opens the pull request. While a run is going, the
"Run the agent" step of its page in the Actions tab shows one line per message
and tool call, without tool output. GitHub serves a step's log through the API
and `gh` only after the step ends, so the page is the place to follow it. See
[`transcripts/`](transcripts).

To keep attempts going unattended, `tools/runner/run_queue.sh` runs a number
of lanes, each taking the next dandiset (those converted by CatalystNeuro
first) through all its roles with `tools/runner/chain.sh`. It waits out the
usage limits, picks up where a stopped chain left off, and then, one attempt
at a time, rebases the branch on main, runs the `recorder` role, which adds
the README row and the pilot notes, and merges the pull request once its
checks pass. With `CLAIMS_ONLY=1`, a runner only reads claims: for each target
whose papers are in the store, it runs the claims and their check and puts the
checked claims on main, and a later attempt on the dataset starts from them.
When a chain stops for a reason a person can fix (a supplement the reader needs, a
claims file that did not pass its check, a failed run), it opens an issue for the
dataset, labelled `needs-you`, that says what stopped it and @-mentions whoever
runs the runner; the issue closes when the dataset is merged, and the Pipeline
page links it. The scripts say how to start and stop it.

## Working on an entry

An entry is a directory under `entries/` with an `entry.yaml`, a
`requirements.in` listing its direct dependencies, and its notebooks, committed
without outputs. One tool does the rest:

```bash
pip install uv pyyaml jsonschema nbformat

python tools/entry.py lock  entries/<name>   # pin the environment
python tools/entry.py check entries/<name>   # metadata and conventions
python tools/entry.py run   entries/<name>   # execute from a clean environment
python tools/entry.py handover entries/<name>  # the verifier's package, without the conclusions
```

The dashboard is a static site built from these files by
`python tools/build_site.py` and republished on every push to `main`: an
overview, a filterable list of dandisets, and a page per attempted dandiset
with its claims and its findings about the data. Every filtered view is a link. `python tools/build_site.py
--demo 150 --output /tmp/demo` builds it from made-up attempts, to see how it
behaves at scale.

Notebooks stream their data from the archive and must compute every result
from it: `check` rejects embedded data, embedded images and figures read from
files. CI runs `check` on every entry and `run` on the entries a change touches.
